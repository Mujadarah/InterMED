Use a **build-only Vite plugin and browser-native classic service worker**, with no extra package. The public shell is small and fixed, and explicit request/cache policy is easier to audit here. `vite-plugin-pwa`/Workbox were considered but not adopted: generic precaching/navigation defaults would still need careful narrowing, and a new compatibility/dependency surface is unnecessary for this milestone. This decision does not forbid reconsideration when later offline requirements exist.

Pinned toolchain: Node **24.21.0**, npm **11.19.0**, Vite **8.3.2**, `@vitejs/plugin-react` **6.1.1**, TypeScript **5.9.3**, Playwright **1.63.0**. No manifest or lockfile dependency change was needed. Context7 Vite 8 documentation and official documentation were consulted on October 1. Actual pinned production builds and browser tests validate the hooks used. Hashing happens in `writeBundle` from **final on-disk bytes**: an earlier `generateBundle` attempt disagreed with Vite's final JavaScript output and was corrected before acceptance.

## Cache, failure and update design

The cache namespace is `intermed-public-shell-v1-<20 hex release identity>`. Identity includes hashes of shell assets and worker policy, never clinical dataset version. Build output permits only generated index/hashed JS/CSS, the manifest and four named icons: at most 16 assets and 2 MiB total. Installation uses no-store, credential-free, redirect-rejecting requests and validates success, MIME type, size and SHA-256 before caching. Incomplete candidates are removed; no network/runtime response is subsequently added to CacheStorage.

Fetch handling covers only same-origin GETs without query or Authorization. Navigation fallback is restricted to the two existing public routes `/` and `/status`. A public static path can hit only an explicitly listed asset in the selected complete release. API, account/admin/auth, external regulatory, secret and patient paths bypass shell handling, as do non-GET, external and query requests. Tests inspect both actual cache keys and cached bodies after prohibited synthetic responses, accounting for worker interception rather than assuming Playwright routing saw every request.

Cached index headers store only public release metadata: identity, exact asset list, actual prior identity and monotonic activation order. They allow a newly natively activated worker whose candidate cache was evicted to serve a **complete previously activated shell**, including its actual old hashed assets. Waiting candidates are excluded from fallback selection. Actual activation order handles rollback/revisit cycles such as A→B→A independently of wall-clock time or CacheStorage insertion order. Status distinguishes worker identity from the served shell and reports prior-shell use without hiding a usable waiting recovery update.

Normal activation retains the current and actual prior shell. A successfully installed waiting candidate can coexist with active/prior shells; replacement of waiting candidates bounds that to three owned caches, then two after activation. Failed install/activation retains a usable prior shell when available. Native activation with an incomplete candidate preserves prior caches. Cleanup matches only this exact namespace plus a valid release identity; it never deletes IndexedDB, preferences or unrelated caches. LocalStorage, an unrelated CacheStorage cache and an IndexedDB test-only canary survive real A→B upgrade.

Unreadable/timed-out active status aborts a replacement before staging or cleanup, preserving prior storage. Confirmed missing/incomplete assets with accessible storage permit replacement. **Retry shell caching** explicitly validates/re-caches an evicted same-build shell, preserves waiting candidates/prior/unrelated storage and does not force reload. Without a controlling worker it retries scoped registration. Persistent storage/network denial still reports unavailable/failure; retry is not a retention guarantee.

Repair failure is reported separately from candidate-update failure. A repair already in flight cannot hide a newer usable waiting candidate; obsolete repair controls are hidden while that update is offered. Focus/status refreshes and page reload retain its explicit activation control. This final interaction failed before the correction (`m2-repair-waiting-red.log`) and passed in 6/6 all-project recovery checks afterward (`m2-repair-waiting-green.log`).

An accessible status/alert announces readiness, unavailable storage and update failure. A waiting update offers **Update shell and reload** with finish-work guidance. Activation checks open in-scope windows and refuses when more than one is open; the user closes other tabs and retries. Reload consent applies only to that explicit action and is cleared on refusal/failure/new candidate. A controller change without consent offers **Reload shell when ready**; it does not force a reload. Browser-native activation after all tabs close is possible and tested separately. Storage exceptions return unavailable status and do not prevent online requests from falling through to the network.

The first-ever offline visit was tested in fresh contexts with no worker/cache: navigation failed and no InterMED heading rendered. **No fallback page was shown or claimed.** After complete caching, offline reload, deep-link navigation and another tab launch succeed. Browser storage may still be evicted/restricted; no permanent retention, private-mode equivalence, installed/tab storage sharing or encryption is promised.
